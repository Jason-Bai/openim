# OpenIM 聊天体验 UI 升级 PRD

日期：2026-05-27
状态：PRD 草稿，待需求评审

## 1. 执行摘要

OpenIM 在进入下一轮实现前，需要让日常聊天体验更清晰、更稳定。本需求升级三个用户直接可见的产品部分：左侧导航侧边栏、OpenClaw 员工助手回复的富文本消息渲染、长会话导航能力。目标是让产品更接近稳定的企业 IM 工具，同时为后续讨论群复用同一套消息渲染基础能力。

## 2. 问题陈述

### 2.1 谁遇到了这个问题

- 登录 OpenIM、浏览会话和通讯录、并与 OpenClaw 员工助手沟通的员工用户。
- 需要判断当前 UI 是否已经具备日常使用成熟度的产品和 QA 评审人员。
- 后续讨论群用户，他们会阅读长文本、结构化内容或生成式消息。

### 2.2 具体问题是什么

当前 UI 在功能上可用，但一些交互细节降低了产品成熟度：

- 左侧侧边栏使用较重的深色块和基础文本按钮，让应用更像原型，而不是成熟的 IM 工作台。
- OpenClaw 员工助手可能返回 Markdown 或 HTML 等结构化文本，但当前消息基本按纯文本展示。
- 长助手回复以及后续讨论群内容可能占据大量屏幕空间，目前缺少折叠机制。
- 当某个会话已有很多回复时，用户需要一个快速回到最新消息的位置，而不是手动滚动。

### 2.3 为什么这是痛点

- 用户无法舒适阅读包含代码、列表、表格、链接或格式化解释的助手回复。
- 长消息降低会话扫描效率，进入讨论群后这个问题会更明显。
- 长会话中的手动滚动会打断核心聊天流程。
- 侧边栏是用户持续看到的主界面元素；如果它显得粗糙，会降低整个产品的稳定感。

### 2.4 依据

- 用户在 2026-05-27 明确提出三个问题：侧边栏视觉质量、OpenClaw 员工助手富文本回复、滚动到底部入口。
- 现有 UI/UX QA 已在 `docs/tests/2026-05-27-ui-ux-qa-optimization-report.md` 中发现交互和信息架构稳定性问题。
- 现有设计文档 `docs/superpowers/specs/2026-05-27-ui-ux-information-architecture-stability-design.md` 明确没有包含完整侧边栏和聊天气泡重设计，因此本需求作为后续补充。

## 3. 目标用户

### 3.1 主要用户：员工聊天用户

- 使用 OpenIM 进行工作沟通。
- 与默认 BOT 和 OpenClaw 员工助手对话。
- 需要清晰稳定的布局和可读性良好的回复。

### 3.2 次要用户：产品 / QA 评审人员

- 验证产品是否像一个 IM 应用，而不是一个原型。
- 需要明确、可验收、可浏览器测试的状态和行为。

### 3.3 未来用户：讨论群参与者

- 阅读长生成内容、总结、代码块和讨论历史。
- 需要一套同时适用于单聊和群聊的消息折叠规则。

## 4. 目标

1. 按企业 IM 视觉方向重设计左侧侧边栏。
2. 新增统一消息内容展示框架，支持纯文本、Markdown、安全 HTML，并能被后续讨论群复用。
3. 新增长内容折叠能力，折叠控制入口位于消息正文顶部。
4. 为长会话新增滚动到底部入口。
5. 保持与现有会话 API 以及当前 React / Vite / Ant Design 技术栈兼容。

## 5. 非目标

本需求不包含：

- 完整移动端导航重设计。
- 主题切换、用户自定义侧边栏、可折叠侧边栏。
- 完整富文本编辑器或富文本消息输入。
- 渲染任意未清洗 HTML。
- 使用 iframe 渲染完整 HTML 应用。
- 讨论群创建或群成员功能。
- 后端 schema 变更，除非后续技术方案证明需要少量 API 元数据补充。

## 6. 产品需求

### 6.1 侧边栏重设计

已确认方向：企业 IM 风格。

需求：

- 将当前较重的深色侧边栏替换为更清爽、克制的 IM 工作台导航。
- 保留现有主导航概念：会话、通讯录。
- 侧边栏结构分为：
  - 品牌区。
  - 主导航区。
  - 当前账号和退出区。
- 当前选中的导航项必须足够明显。
- 导航项保留图标 + 文案，保证清晰度。
- 设计应体现工作场景下的稳定和克制，更接近飞书 / Slack，而不是开发者工具或营销型 SaaS 页面。
- 窄屏下优先保留当前顶部横向导航行为，除非技术方案确认存在低风险优化。

验收标准：

- 用户不需要阅读主面板标题，也能识别当前所在模块。
- 账号名称可读，不会溢出侧边栏。
- 退出操作始终可用，并有稳定的可访问名称。
- 桌面端和小于等于 860px 宽度下，不引入页面级横向滚动。

### 6.2 统一消息渲染器

为所有会话消息建立可复用的消息渲染模型。

支持内容：

- 纯文本。
- Markdown。
- 安全 HTML 子集。

Markdown 支持应包含：

- 段落。
- 加粗和斜体。
- 行内代码。
- 围栏代码块。
- 列表。
- 引用块。
- 如果所选 Markdown 库支持 GitHub Flavored Markdown，则支持表格。
- 链接。

安全 HTML 应只允许基础阅读类标签，例如：

- `p`、`br`、`strong`、`em`、`u`、`s`
- `ul`、`ol`、`li`
- `blockquote`
- `code`、`pre`
- `table`、`thead`、`tbody`、`tr`、`th`、`td`
- `a`

后续技术方案可根据 sanitizer 库的能力微调具体 allowlist。

安全要求：

- 不渲染未清洗 HTML。
- 移除脚本、样式、iframe、事件处理属性、危险 URL、内联 JavaScript。
- 链接在新窗口 / 新标签打开，并带安全 `rel` 属性。
- 渲染后的内容不能突破消息气泡边界，也不能覆盖无关 UI。

验收标准：

- OpenClaw 员工助手返回的 Markdown 内容能按格式渲染，而不是显示原始 Markdown 文本。
- 安全 HTML 示例能按支持的格式渲染。
- 不安全 HTML 示例不会执行脚本或事件处理器。
- 代码块和表格可读，且不会导致页面级横向滚动。
- 渲染器能被后续讨论群消息复用，不需要重复实现。

### 6.3 长消息折叠

长消息应按渲染后的实际高度折叠，而不是只按原始字符数判断。

需求：

- 如果渲染后的消息超过配置的折叠高度，默认展示折叠状态。
- 折叠控制入口显示在消息正文顶部。
- 折叠状态文案：`展开全文`。
- 展开状态文案：`收起`。
- 内容预览显示在顶部控制入口下方。
- 折叠优先适用于 OpenClaw 员工助手消息，但组件应支持用户消息和后续讨论群消息复用。
- 代码块和表格可保持各自内部滚动。

推荐默认阈值：

- 初始折叠最大高度：360px。
- 技术方案可在浏览器 QA 后调整该值。

验收标准：

- 长 Markdown 回复默认折叠。
- `展开全文` 显示在内容预览上方。
- 点击 `展开全文` 后展示完整内容，且不会异常丢失滚动位置。
- 点击 `收起` 后恢复折叠状态。
- 短消息不显示折叠控制入口。

### 6.4 滚动到底部入口

长会话需要提供快速回到最新消息的方式。

行为：

- 如果用户接近底部，新消息自动滚动到最新消息。
- 如果用户已手动离开底部，新消息不强制滚动，不打断阅读。
- 当用户离开底部时，在会话区域右下角显示向下箭头按钮。
- 如果用户离开底部期间收到新消息，在按钮附近显示 `新消息` 提示。
- 点击按钮后滚动到底部，并清除新消息提示。

验收标准：

- 打开长会话时，如果最新消息不可见，可以显示滚动到底部按钮。
- 用户手动向上滚动后显示按钮。
- 点击按钮后滚动到最新消息。
- 用户已经接近底部时发送消息，会自动跟随到最新消息。
- 用户正在阅读旧内容时收到消息，不会被强行打断。

## 7. 用户故事

### Story 1：侧边栏像稳定的 IM 工作台

作为员工，我希望左侧导航清爽、易扫描，这样我能把它当作日常工作聊天工具来使用。

验收标准：

- 侧边栏使用企业 IM 视觉方向。
- 会话和通讯录仍然一键可达。
- 当前模块、当前账号、退出操作分区清晰。

### Story 2：OpenClaw 员工助手回复可读

作为员工，我希望 OpenClaw 员工助手返回的 Markdown 或安全 HTML 能正确渲染，这样我能自然阅读结构化答案、代码和表格。

验收标准：

- Markdown 示例正确渲染。
- 安全 HTML 示例经过清洗后正确渲染。
- 不安全 HTML 被中和。

### Story 3：长助手回复不会淹没会话

作为员工，我希望长助手回复默认折叠，并在顶部提供展开入口，这样我能快速扫描会话，并在需要时阅读全文。

验收标准：

- 长内容默认折叠。
- `展开全文` 显示在顶部。
- 展开后可以再次收起。

### Story 4：长会话易于导航

作为员工，我希望有一个快速回到最新消息的入口，这样我不需要在长会话里手动滚动。

验收标准：

- 在合适时机显示右下角入口。
- 新收到的消息不会打断用户阅读旧内容。
- 点击入口后回到最新消息。

## 8. 依赖

技术方案阶段需要评估的技术依赖：

- Markdown 渲染库。
- HTML sanitizer 库。
- 消息内容是否需要明确的格式元数据，还是可以先用 Markdown 渲染 + HTML 清洗的默认策略。
- 现有消息列表 DOM 结构和滚动容器行为。
- 现有消息气泡和响应式布局 CSS 约束。

产品依赖：

- 本需求假设当前会话和 OpenClaw 员工助手消息流程继续保持。
- 讨论群功能属于未来工作，但本渲染器不能阻碍后续复用。

## 9. 风险与缓解

### 风险：HTML 渲染引入安全问题

缓解：

- 使用 sanitizer 库。
- 维护窄 allowlist。
- 增加危险 HTML 的测试或浏览器 QA 用例。

### 风险：Markdown / HTML 识别存在歧义

缓解：

- 技术方案阶段决定是否需要显式消息格式元数据，还是使用安全默认 Markdown 渲染策略。
- 如果后端暂时没有元数据，前端可以先把助手文本按 Markdown 处理，并清洗其中产生或包含的 HTML。

### 风险：折叠破坏代码块或表格可读性

缓解：

- 测试长代码块和表格。
- `pre` 和表格容器保留内部滚动。
- 基于渲染后高度进行折叠。

### 风险：滚动到底部逻辑干扰用户阅读

缓解：

- 使用接近底部阈值。
- 只有用户已经接近底部或主动发送消息时才自动滚动。
- 用户离开底部时保留未读 / 新消息提示。

## 10. 建议 Issue 拆分

在 PRD 和技术方案确认后，按独立可交付功能创建 GitHub Issue：

1. 侧边栏重设计。
2. 支持 Markdown、安全 HTML 和长内容折叠的消息渲染器。
3. 滚动到底部入口。

消息渲染器 Issue 风险最高、体量最大，因为它涉及安全边界和后续讨论群复用。

## 11. 验证计划

PRD 层验证：

- 产品评审确认视觉方向、折叠控制位置、滚动行为。
- 技术评审在编码前确认安全渲染方案。

实现层验证稍后在技术方案中定义：

- 前端 build / typecheck。
- 桌面端和小于等于 860px 宽度的浏览器 QA 截图。
- 手工富文本用例：
  - Markdown 标题 / 列表 / 代码 / 表格。
  - 安全 HTML 段落 / 列表 / 表格 / 链接。
  - 带 script / 事件处理器的不安全 HTML。
  - 长助手消息折叠和展开。
  - 长会话滚动到底部行为。

## 12. 开放问题

当前讨论中没有剩余产品阻塞问题。

技术方案仍需决定：

- 具体 Markdown 和 sanitizer 库。
- 是否现在增加内容格式元数据，还是延后。
- 浏览器 QA 后确定折叠高度和接近底部滚动阈值。
